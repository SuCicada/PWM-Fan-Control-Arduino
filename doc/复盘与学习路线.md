# 项目复盘与嵌入式学习笔记

这份文档基于 2026-08 的一次全面代码审查和重构整理而成。分四部分：项目原理、踩过的坑（复盘）、深入知识点、学习路线。

---

## 一、这个项目的原理

### 1.1 整体架构

```
┌─────────────┐  nvidia-smi   ┌──────────────────┐   USB 串口 9600   ┌──────────────┐  PWM   ┌────────┐
│  NVIDIA GPU │ ────────────> │ Go 控制程序 (PC)  │ <──────────────> │ Arduino Nano │ ─────> │ 4线风扇 │
│  (温度)      │               │ 温度→转速决策     │   文本协议+CRC8   │ (ATmega328P) │ <───── │        │
└─────────────┘               └──────────────────┘                  └──────────────┘  TACH  └────────┘
```

职责划分：

- **Go 程序**（`tool/gpu_fan_auto_control-go/`）：读 GPU 温度，查配置表算目标转速，通过串口下发，再读回验证。它是"大脑"，一次性运行，靠 cron/systemd timer 周期调度。
- **Arduino 固件**（`src/`）：接收指令、输出 PWM、统计转速、每秒播报状态。它是"手"，不做决策，但要保证自身永远可用（看门狗、EEPROM 断电恢复）。

这种"决策在 PC、执行在 MCU"的分层是嵌入式系统里很典型的结构。MCU 侧越笨越好——逻辑简单意味着不容易死、容易验证。

### 1.2 四线 PWM 风扇

四根线：电源、地、PWM 控制、TACH 转速反馈。

- **PWM 线**：风扇内部驱动电路按占空比调速。注意是风扇自己解读占空比，不是靠 PWM 直接斩波供电，所以即使 PWM 频率不理想风扇也能转（见 3.1）。
- **TACH 线**：开集电极输出，每转输出 2 个脉冲（业界惯例，但非绝对，见 3.2）。开集电极意味着必须有上拉——代码里用 `INPUT_PULLUP` 启用了 MCU 内部上拉。

### 1.3 通信协议

```
请求（PC → Arduino）:  fanpwm:<speed>:<seq>:<crc8>\n
响应（Arduino → PC）:  fanpwm:<rpm>:<speed>\n
```

- `speed`：0-255，直接对应 `analogWrite` 的占空比。
- `seq`：随机序号。固件按"整行内容"去重，seq 的存在让"同一转速的两次独立指令"不会被误判为串口抖动造成的重复帧。
- `crc8`：对 `fanpwm:<speed>:<seq>` 计算，参数 poly 0x07 / init 0x00 / 不反转。两端必须选同一套参数——CRC8 有十几种变体，这是跨语言协作时最容易踩的坑。Go 测试里用标准检验值（`"123456789"` → `0xF4`）把算法钉死了，选错会先在测试里炸而不是在串口上疑难杂症。

为什么要 CRC：串口本身没有完整性保证，USB 转串口芯片、电磁干扰、缓冲区截断都可能造成坏字节。对"控制散热"这种指令，宁可丢弃重发也不能执行错的。

### 1.4 固件的自我保护

- **看门狗（WDT）**：`wdt_enable(WDTO_2S)` + 主循环里 `wdt_reset()`。程序死循环或跑飞时硬件强制复位。关键原则：**看门狗防的是"死"，不是"错"**——喂狗不应该以业务逻辑成功为条件（这次踩过的坑，见 2.1）。
- **EEPROM 记忆**：转速存进 EEPROM，断电/复位后恢复。配合看门狗，即使固件崩了重启，风扇转速也不会跳变。
- **主循环非阻塞**：逐字节收串口、`millis()` 节拍报转速，任何一轮循环耗时都在几百毫秒内，看门狗永远有余量。

### 1.5 Go 侧的控制逻辑

- 温度→转速是**阶梯查表**（`config.yml` 的 `fan_level`），不是 PID。对散热这种慢系统，查表+迟滞足够，还容易理解和调试。
- **迟滞（hysteresis）**：升温立即升档，降温要求比阈值再低 N 度才降档。没有它，温度在阈值附近抖动时风扇会来回跳，比恒速还吵。
- **读回验证**：下发后持续读状态帧直到转速匹配。串口是不可靠信道，"发了"和"生效了"是两件事。

## 二、这次出过的问题（完整复盘）

按严重程度排序。每一条都值得记住，因为它们全是嵌入式的经典坑。

### 2.1 `Serial.readString()` 的超时语义 → 看门狗连环重启（根因级 bug）

**现象**：Go 程序读回的数据里混着 `setup start` 启动横幅，当时在 Go 里写了段特判去跳过它——这其实是在给"板子每收一条指令就重启一次"打补丁，而没意识到板子在重启。

**根因链**：

1. `Serial.readString()` 不是读到换行返回，而是**一直读到超时**（默认 1000ms）。
2. 于是每收到一条指令，loop 耗时 = 打印 ~70ms + readString 1000ms + `delay(1000)` ≈ 2.07s。
3. 看门狗设的是 `WDTO_2S`。超了。每条指令都触发复位。
4. 更糟的是 `wdt_reset()` 写在 `if (ok)` 里——CRC 错误或乱码也不喂狗，等于一条坏数据主动申请重启。

**教训**：

- **调 API 之前搞清楚它的阻塞/超时语义**，尤其是 Arduino 的 `Stream` 系列（`readString`、`readStringUntil`、`parseInt` 全是超时驱动的）。
- **在下游打补丁之前，先问为什么会有这个现象**。`setup start` 出现在数据流里本身就是"板子在重启"的铁证，当时离真相只差一步。
- 看门狗喂狗必须无条件（只要主循环还活着就喂），业务错误用日志和协议层处理。

### 2.2 RPM 读数错误（README 里挂了很久的 TODO）

三个独立错误叠加：

1. **`CHANGE` 边沿双倍计数**：中断挂在 `CHANGE` 上，一个脉冲的上升沿+下降沿各触发一次。风扇每转 2 脉冲 → 每转实际 4 次计数，代码却除以 2，读数直接翻倍。
2. **时间基准是假设的**：`rpm = count * 60` 隐含"刚好过了 1 秒"，但受 2.1 影响实际间隔在 1~2 秒间浮动，读数忽高忽低。修法：用 `millis()` 记录真实间隔换算。
3. **非原子读取**：`pulseCount` 是 4 字节的 `unsigned long`，8 位 AVR 读它要 4 条指令，ISR 可能在中间插进来造成"撕裂读"。修法：`ATOMIC_BLOCK` 里快照+清零。

**教训**：传感器读数不对时，把"计数"、"时基"、"读取方式"三个环节分开排查。当时代码里留着 `// 尝试上升沿` `// 尝试任意边沿` 的注释——方向对了，但只在第 1 个环节里试错，而真正的问题横跨三个环节。

后来 PWM 改到 Timer1 25kHz 之后，又冒出第四个问题：中间占空比时 PWM 串进 TACH，边沿中断和「最小间隔去抖」都会读出几万转。完整过程见 [tach-pwm-串扰与测速.md](./tach-pwm-串扰与测速.md)。

### 2.3 `new` 出来的对象从没 `delete` → 内存泄漏

`ReqData::NewFromString` 每条合法指令 `new` 一个对象，任何路径都没有释放。ATmega328P 只有 **2KB RAM**，一条漏十几字节，跑几天必然堆耗尽。而且大量使用 `String` 拼接，堆碎片本身就是 AVR 的经典死因——看门狗多半一直在掩盖这类偶发崩溃。

**修法与教训**：小 MCU 上**默认不用堆**。栈上的值类型 + 固定 `char` 缓冲区 + `strchr`/`atoi`/`snprintf`，重构后全程序 RAM 占用 285 字节、全部静态可预测。"能不能跑"和"能不能跑三个月"是两个标准。

### 2.4 Go 的 `(nil, nil)` 返回 → 必然触发的空指针 panic

`readFanFromSerial` 在"没扫到状态行"时返回 `(nil, nil)`——err 是 nil。三个调用方都只查了 err 就解引用。配合 2.1（板子刚重启时只有横幅没有状态行），这不是理论风险而是必现崩溃。

**教训**：Go 里 `(nil, nil)` 是留给"合法的空结果"的，"没拿到该拿的东西"必须是 error。这条连老手也常犯，因为类型系统拦不住。

### 2.5 死配置：`serial_port` 写了但没人读

结构体里定义了、YAML 里写了，但代码只用 `-port` flag。用户改配置文件完全没反应，还以为生效了。**"看起来能配置其实不能"比"不能配置"危害大**。修法：明确优先级（flag > 配置文件 > 默认值）并写进 `-help`。

### 2.6 EEPROM 空白值歧义

擦除态的 EEPROM 读出来是 `0xFF` = 255，恰好是合法的最大转速——首次上电会直接满速。修法：用独立地址存一个魔数（`0xA5`）标记"确实写过"。**任何"用数据本身的取值判断数据是否有效"的方案，都要先问一句：无效状态的默认值会不会恰好落在合法区间里。**

### 2.7 无迟滞的阶梯控制 → 转速在阈值附近震荡

温度在 30°C 上下抖动时，风扇在 50/150 之间来回跳。任何"连续量→离散档位"的映射都需要迟滞（恒温器、电池电量格、信号强度格全是同一个问题）。

### 2.8 测试没有断言

原来的测试只是 `fmt.Println`，永远不会失败，等于没测。协议编解码这种纯函数是最值得测的：输入输出明确、不需要硬件、还能把跨语言约定（CRC 参数）钉死。

### 2.9 一个反面教训（审查者也会犯错）

审查时我判断 `fprintf(Serial, "%l", ...)` 里的 `%l` 是非法格式符——按标准 C 确实是，但 StringUtil 库自定义了一套格式符，`%l` 就是 long。同时我以为 `paulstoffregen/Time` 是没人用的依赖，实际它是 StringUtil 的硬依赖（`StringUtil.cpp` 里 `#include <TimeLib.h>`）。

**教训（对双方都成立）**：判断一段代码"有没有 bug"之前，先确认它调的到底是什么实现。嵌入式世界里非标准的自制轮子非常多，不能拿标准库的语义去套。

## 三、深入知识点

### 3.1 PWM 频率：这个项目还藏着一个没爆发的问题

Intel 四线风扇规范要求 PWM 控制频率在 **21-28kHz（目标 25kHz）**。而 Arduino `analogWrite` 在 Nano 的 Pin 5 上用的是 Timer0 默认配置，只有约 **976Hz**。

为什么现在能用：多数风扇驱动 IC 对低频 PWM 有容忍度，会做平均。但代价可能是：某些占空比下风扇发出电流声（whine）、低占空比下转速不线性、个别风扇直接不理会。

如果将来想做对：

- Pin 5/6 挂在 Timer0 上，**动它的分频会破坏 `millis()`/`delay()`**，不要碰。
- 正确姿势是把 PWM 移到 Pin 9 或 10（Timer1），用 ICR1 做 TOP：16MHz / 25kHz / 2（相位修正模式）= 320。这是标准的"25kHz 风扇 PWM"配方，网上搜 "Arduino Timer1 25kHz fan" 有成熟代码。
- 这件事会逼你第一次直接读写定时器寄存器（TCCR1A/TCCR1B/ICR1/OCR1A），是从"Arduino API 用户"迈向"看数据手册编程"的绝佳台阶。

### 3.2 TACH 与转速测量的门道

- 每转 2 脉冲是惯例不是标准，换风扇后先验证（拿已知转速对表，读数差整数倍就是脉冲数假设错了）。
- 数脉冲（本项目的做法）适合高转速；测**脉冲间隔**（`micros()` 差值）适合低转速、响应更快。工业上常两者结合。
- TACH 信号可能有毛刺。偶发尖峰可以用「最短间隔」丢掉；PWM 这种一直在的载波不行——去抖只会把它降采样成假转速。本项目用的是「同一电平稳住 1ms 才算翻转」，详见 [tach-pwm-串扰与测速.md](./tach-pwm-串扰与测速.md)。

### 3.3 `volatile`、原子性与 ISR 通信

这次踩的坑值得展开成三条通用规则：

1. **ISR 和主循环共享的变量必须 `volatile`**——阻止编译器把它缓存在寄存器里。
2. **`volatile` 不等于原子**。8 位机上超过 1 字节的读写都可能被中断撕裂。要么 `ATOMIC_BLOCK`，要么把共享变量降到单字节。
3. **ISR 里只做最少的事**（本项目只有 `pulseCount++`，是对的）。不打印、不算浮点、不碰串口——这些要么慢要么本身依赖中断。

### 3.4 看门狗的哲学与 AVR 的坑

- 定位：**最后一道防线**，不是错误处理机制。触发一次看门狗复位 = 有一个没查明的 bug，要当事故看，不能当日常。
- 超时选择：正常主循环最大耗时 × 5~10 倍。这次从 2s（余量不足）→ 临时 8s（掩盖问题）→ 修好根因后回到 2s（余量 5 倍），是个完整的教学案例。
- AVR 特有的坑：看门狗复位后 **WDT 仍然是使能的**，且超时被重置为最小值。老式 bootloader 不清 WDT 会导致复位循环（Optiboot 处理了）。所以在 `setup()` 尽早处理 WDT 状态是 AVR 的老规矩。

### 3.5 串口通信的可靠性分层

一条不可靠的字节流做到可靠指令下发，本项目正好集齐了完整分层，每一层解决一个问题：

| 层 | 手段 | 解决什么 |
|---|---|---|
| 帧定界 | `\n` 结尾，逐字节攒行 | 从字节流里切出完整消息 |
| 完整性 | CRC8 | 坏字节不被执行 |
| 幂等 | 按整行去重 + seq | 重发不产生副作用 |
| 确认 | 读回状态帧验证 | "发了"≠"生效了" |
| 超时 | 各层都有 deadline | 任何一步卡死都能退出 |

工业协议（Modbus、CAN 应用层）本质上就是这套东西的标准化版本。自己完整实现过一遍，再学它们就是"哦，一样的"。

遗留的不对称：**响应方向没有 CRC**，而验证恰恰依赖响应。补齐它需要固件和 PC 端同步升级——协议变更的版本管理本身也是个值得练的题目（常见做法：响应里带协议版本号，或新旧格式并行一段时间）。

### 3.6 EEPROM 的寿命账

ATmega328P 的 EEPROM 标称 10 万次擦写。听着多，算笔账：如果每分钟温度波动导致一次档位切换并写 EEPROM，10 万次 ≈ 69 天。本项目的防线：`EEPROM.update()`（值没变不写）+ 上层去重 + 迟滞减少切换次数。写入更频繁的场景要上磨损均衡（把写入轮转到多个地址）。

### 3.7 两个容易忽视的正确性细节

- **`millis()` 溢出**：约 49.7 天回绕一次。`now - last >= interval` 用无符号减法天然处理回绕，是对的；`now >= last + interval` 是错的。定时逻辑永远写成前者。
- **串口打印的时间成本**：9600 波特 ≈ 每字节 1.04ms。一段 100 字节的调试输出就是 100ms——在有看门狗和实时性要求的循环里，打印本身就是显著的延迟来源。这也是嵌入式日志常用"级别开关 + 提高波特率 + 精简输出"的原因。

## 四、嵌入式成长路线

结合这次暴露的知识缺口，按依赖顺序排的建议。每一步都给出"用这个项目怎么练"。

### 第 1 步：吃透手上这块 ATmega328P（1~2 个月）

目标：从"调用 Arduino API"变成"知道 API 底下是哪个寄存器"。

- 下载 **ATmega328P 数据手册**，只精读三章：I/O Ports、Timer/Counter、USART。对照着回答：`analogWrite(5, 128)` 到底配置了哪几个寄存器？`Serial.begin(9600)` 的波特率是怎么从 16MHz 算出来的？
- **实战任务：把风扇 PWM 改成 Timer1 的 25kHz**（见 3.1）。做完这一个任务，定时器这章就通了。
- 读一遍 Arduino core 的源码（`wiring.c` 里的 `millis()` 实现、`HardwareSerial` 的中断驱动环形缓冲区）。后者就是你这次手写"逐字节攒行"的官方版本，对照着看收获很大。

### 第 2 步：C 语言的嵌入式子集（并行进行）

这次的坑指明了重点：指针与生命周期（2.3 的泄漏）、`volatile` 与内存模型（2.2 的撕裂读）、整型提升与溢出（`counts * 60000UL` 里那个 `UL` 不是装饰）、位运算。推荐把 *The C Programming Language*（K&R）过一遍，薄，但每一页都有用。C++ 在小 MCU 上只用"更好的 C"子集：struct + 成员函数、`constexpr`、引用，避开异常/RTTI/大量模板/动态分配——这次重构后的 `data.h` 就是这个风格。

### 第 3 步：买一台逻辑分析仪（随时，越早越好）

十几块钱的 8 通道 24MHz 小盒子（配 sigrok/PulseView）就够。这次如果有它，把 TACH 线接上一看波形，"CHANGE 双倍计数"当场现形，不用猜三种边沿模式。**嵌入式调试的本质是观测手段的竞争**——printf 只能看软件以为发生了什么，逻辑分析仪能看真的发生了什么。下一档是入门示波器（看模拟波形、电源纹波），可以晚点买。

### 第 4 步：换平台，见识 32 位（3~6 个月后）

- **ESP32**：便宜，双核 240MHz + WiFi/BLE，FreeRTOS 原生。适合把本项目升级成"网页看温度曲线、手机调风扇"——顺便逼你学 RTOS 的任务、队列、互斥量。
- **STM32**（比如 F103/G0 系列 + STM32CubeIDE）：工业界主流，HAL 库 + 寄存器双修，有真正的调试器（SWD 断点单步，从此告别 printf 调试）。DMA、多路定时器、硬件 CRC 外设——你会发现这次手算的 CRC8 人家有硬件单元。
- 顺序建议：先 ESP32（成就感快），再 STM32（走得深）。

### 第 5 步：RTOS 与并发思维

本项目的 `loop()` 是"超级循环"（super loop）架构，够用但有天花板：任务多了以后互相阻塞。FreeRTOS 解决的就是这个。学习路径：把本项目移植到 ESP32 + FreeRTOS，拆成三个任务——串口协议任务、转速测量任务、控制任务，用队列传消息。做完你会真正理解这次"非阻塞改造"其实是在超级循环里手工模拟调度器。

### 第 6 步：协议与总线

按使用频率：**UART**（这次已经吃透）→ **I2C**（接个温度传感器如 SHT31，就不用依赖 nvidia-smi 了）→ **SPI**（接个 OLED 屏显示转速）→ **CAN**（如果往车载/工业方向走）。每学一个总线，用逻辑分析仪抓一次波形看时序，印象完全不同。

### 第 7 步：工程化习惯（贯穿始终）

这次重构做的事就是清单：

- 纯逻辑（协议编解码、温度映射）与硬件隔离，前者上单元测试；
- 跨端约定（CRC 参数、帧格式）用测试钉死；
- 一切阻塞调用都要有超时，一切超时都要有依据；
- 错误路径和成功路径同等对待（错误要能被 cron/监控看见）;
- 文档记录"为什么"而不只是"是什么"（比如为什么看门狗是 2s、为什么每转 4 计数）。
